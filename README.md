## Building

On Linux, build Windows plugins with the MinGW-w64 `x86_64-w64-mingw32` GCC/G++
cross compiler:

```sh
cmake --preset mingwcross-debug
cmake --build --preset mingwcross-debug -j 4
```

This writes Windows plugin and tool DLLs to `build/mingwcross-debug/plugins` and
`build/mingwcross-debug/tools`. Use `mingwcross-release` for a stripped release
build. Copy these directories into the matching SRZ80 Windows distribution's
`bin/` directory; that distribution supplies the MinGW runtime DLLs.

## Card execution-state format

If your card saves execution state, use `<state.hpp>` from `sdk/helpers`.
It wraps your payload in a 28-byte envelope. All integer fields use
little-endian order.

| Offset | Bytes | Field |
| --- | --- | --- |
| 0 | 8 | `SRZ80ST` followed by NUL |
| 8 | 2 | Envelope version, currently 1 |
| 10 | 2 | Header size, currently 28 |
| 12 | 4 | Card payload version, currently 1 for each card |
| 16 | 8 | Payload byte count |
| 24 | 4 | FNV-1a 32-bit checksum of the payload |
| 28 | variable | Card-specific payload |

The checksum uses FNV-1a with offset basis 2166136261, prime 16777619, and
unsigned 32-bit wrapping. It detects corruption, but it does not authenticate
the data. The host already associates each blob with its card, so the envelope
does not include a plugin ID.

Write private `save_payload` and `load_payload` functions with the
`SrhSaveState` and `SrhLoadState` signatures. Register them through the shared
callbacks:

```cpp
#include <state.hpp>

using State = srz80::sdk::state::Callbacks<save_payload, load_payload, 1>;
// In SrhPlugin: ..., State::save, State::load, &descriptor, ...
```

The adapter handles size queries with a null buffer, short buffers, overflow,
exceptions, header validation, exact envelope length, and the checksum. An
empty payload still gets a 28-byte envelope. Increase the third template
argument when you change the payload layout or what its fields mean. Your
serializer writes only the payload. It does not need its own magic, version,
or checksum. You can put a hardware or configuration identifier at the start
of the payload, such as the VDP model, YM2414 backend, or SWP00 clock.

Use `state::Writer` and `state::Reader` for fields, and `state::copy_payload`
for buffer handling. `fields(...)` writes fixed-width integers in
little-endian order, booleans as 0 or 1, IEEE floating-point bit patterns,
and arrays one element at a time. Write enums as explicit fixed-width integers
and check their allowed values when loading. Check `Reader::finished()` before
you commit decoded fields. For a fixed layout, you can use `state::put<T>` and
`state::get<T>` after checking the full buffer size. You can copy byte arrays
and UTF-8 JSON payloads directly. Do not save native structs, padding,
pointers, or native-endian multibyte values.

Load into temporary state first. Check lengths, configuration, enum values,
and valid ranges before you change the live card. If the card owns host
registrations or other resources that cannot be copied, stage only the fields
or core you can restore. The envelope cannot validate your payload for you.
Existing register-only snapshots still contain only registers. The shared
envelope does not add DSP history.

Only this format is accepted. You cannot load earlier unframed snapshots or
old payload versions. Project chunks from `save_project_data` and
`load_project_data` use a separate format, as do GUI tool project documents.
W65C816 does not expose execution-state callbacks.

## Testing a card

Test your card through two public interfaces:

- The headless `srz80` loader checks discovery, ABI, configuration, and
  rejection paths.
- The engine ABI in `sdk/include/srz80/engine.h` lets you run deterministic
  simulations and check register behaviour.

Use these interfaces for card validation. Do not use `srz80_gui`, modify SRZ80,
link against private host libraries, or write a fake host ABI harness.

### Set up a test distribution

Do your test work in `scratch/`, which Git ignores. Copy the compiled SRZ80
distribution there, then put your plugin in the `plugins/` directory beside
the loader:

```sh
mkdir -p scratch/card-test/plugins
cp -a /path/to/srz80-dist/. scratch/card-test/
cp build/gcc-debug/plugins/<your_plugin>.so scratch/card-test/plugins/
```

The loader finds plugins relative to its executable. Run the tests from
`scratch/card-test`. These commands use a POSIX shell. On Windows, use
`Copy-Item` and `srz80.exe` instead.

### Check the card's requirements

Read `sdk/include/srz80/abi.h` and `sdk/include/srz80/engine.h`. Check the
card's source or documentation for:

- `SrhPlugin::id`, which goes in the project's `"plugin"` field. It may differ
  from the DLL or SO filename.
- The address space, `base`, and inclusive mapping range
  (`base..base + size - 1`).
- The clock index, image slots, JSON config keys, signal names, reset
  behaviour, and save/load state format.

### Check loading and configuration

Create small project-v2 JSON files beside any ROM or image files the card
needs. This example maps 16 I/O bytes starting at `0xC0`:

```json
{
  "version": 2,
  "seed": 1,
  "epoch_ns": 0,
  "time_mode": "project",
  "spaces": [
    {
      "name": "cpu0.io",
      "maximum": "0xFF",
      "resolver": "priority",
      "unclaimed": "0xFF"
    }
  ],
  "clocks": [0, 0, 0],
  "cards": [
    {
      "plugin": "my_cool_card",
      "space": "cpu0.io",
      "base": "0xC0",
      "size": 16,
      "priority": 0,
      "config": {}
    }
  ]
}
```

Set `space`, `base`, `size`, `clock`, `config`, and `image` to the values your
card needs. Run the headless loader:

```sh
cd scratch/card-test
./srz80 case-valid/project.json
echo $?   # 0 = clean load, nonzero = validation/load failure
```

The loader should report a card count that includes your card, with no ABI,
export, dependency, configuration, or mapping error.

Try each invalid case on its own:

- Unknown plugin ID.
- Missing required space.
- Out-of-range or overlapping `base` or `size`.
- Malformed config JSON or a value with the wrong type.
- Missing or bad image.
- Invalid signal name.
- Missing required host capability or extension.

Each case should exit with a nonzero status. Check that it does not crash,
hang, or leave a partly loaded rack.

### Run the card with `engine.h`

The headless loader initializes a project but does not run it. To check
registers, clocks, interrupts, and resets, build a small CLI program against
the public engine ABI from the repository root:

```sh
g++ -std=c++20 -I sdk/include \
    -L scratch/card-test -Wl,-rpath,$PWD/scratch/card-test \
    scratch/your_card_test.cpp -lsrz80engine \
    -o scratch/your_card_test
```

Your program can use:

- `srz80_engine_create` and `srz80_engine_destroy`.
- `srz80_engine_load_project` /
  `srz80_engine_load_project_json`.
- `srz80_engine_find_space`, `srz80_engine_cards`, and
  `srz80_engine_clocks`.
- `srz80_engine_read` and `srz80_engine_write` for bus accesses.
- `srz80_engine_resume` followed by
  `srz80_engine_run(engine, ticks, UINT64_MAX)` to advance a known number of
  clock events.
- `srz80_engine_sample_signal`, `srz80_engine_drive_signal`,
  `srz80_engine_subscribe_signal`, and `srz80_engine_release_signal`.
- `srz80_engine_properties` and `srz80_engine_edit_property`.
- `srz80_engine_text_query` for text/UART observables.
- `srz80_engine_save_state` and `srz80_engine_load_state`.
- `srz80_engine_now`, `srz80_engine_stop_reason`, and
  `srz80_engine_run_state`.

Use `srz80_engine_candidate_create` and `srz80_engine_replace` if you need to
keep the active rack running while you load a replacement.

To test CPU, interrupt, or full-system behaviour, add compatible CPU, RAM, and
ROM cards. Write a small deterministic guest program, run it, and check a
memory address, signal, text endpoint, or provider for the expected result.

### Check the card's behaviour

For each exposed register or mapped byte, check:

- The first and last mapped addresses.
- One byte just below and above the mapping.
- Reset defaults, cold reset, and warm reset.
- Read and write masks, read-only and write-only behaviour, FIFO, status,
  acknowledge behaviour, and side effects.
- Clock-driven or scheduled behaviour.
- Signal assertion and release.
- `peek` reads that leave the card's state unchanged.

Run each project more than once with a fixed `seed` and
`"time_mode": "project"`. The results should match each time.

### Record the results

For each test, keep the project JSON, build command, test command, expected
result, actual result, and complete host log. Say what you could not check.
Without a guest CPU, RAM, ROM, or suitable provider, you can check discovery,
ABI compatibility, configuration, and lifecycle behaviour, but you may not be
able to check private callbacks or every register behaviour.

A crash, access violation, hang, inconsistent result, or successful load with
the wrong mapping or configuration is a failure.
